# TonyAI: Security model

> Moved from [`README.md`](../../README.md) on 2026-11-05 (OpenSpec change `refactor-readme`); the text is unchanged.

## How it works (request lifecycle)

1. The user signs in on **`/login`**; `@supabase/ssr` stores the session (a JWT) in cookies. An account starts from an emailed invitation, and "Forgot your password?" emails a reset link; both land on **`/auth/confirm`**, which signs the person in with the link's one-time token, and then **`/auth/set-password`** (LP4-01).
2. **`proxy.ts`** protects every route — unauthenticated users are redirected to `/login`; only `/login`, `/forgot-password`, `/auth/confirm` and `/auth/set-password` are reachable without a session. (Next.js 16 renamed the `middleware` file convention to `proxy`; same behaviour.)
3. The frontend calls the API through **`apps/web/lib/api.ts`**, attaching `Authorization: Bearer <access_token>`.
4. The NestJS **`SupabaseAuthGuard`** verifies the JWT (shared HS256 secret or asymmetric via JWKS — see Security model), loads the user's `Profile` — refusing a disabled account, or a member of an offboarded organisation, with 401 `account_disabled`, and a token whose session began at or before the account's `sessions_revoked_at` with 401 `session_revoked` — the web answers both by signing the session out — and computes **`accessibleSubsidiaryIds`** (a `super_admin` and a `standard_user` are limited to their same-organisation grants; a `masterkey` and an `auditor` get the whole organisation; a role the build does not know gets nothing) and, for a `standard_user`, **`categoryGrants`** (the categories ticked on each grant). The role is read from the profile on every request, so no token carries a stale role.
5. Services scope **every query** to that set, and every read of activity records, and of figures built from them, to the record scope (`recordScopeWhere`, which adds a standard user's categories). Write authority is one capability table, `ROLE_CAPABILITIES` in `@tonyai/shared-types`, asked as `can(role, capability)`: **organisation structure** (subsidiaries, period locks, targets, denominators, the inventory boundary, report capture and issue) is the `masterkey`'s alone, **facilities** the masterkey's and a `super_admin`'s in its granted companies, **activity data + evidence** the author's (a `masterkey`, `super_admin` or `standard_user`, the last within its categories), **review, return and approve** the record's routed approver (`recordApprover`: a `super_admin` of the company or a `masterkey`), and **void** the masterkey's alone; an `auditor` writes nothing. Each mutation writes an `audit_log` row.
6. **Row Level Security** in Postgres independently denies cross‑tenant reads, so even a direct database/PostgREST client is contained.

## Security model

Tenant isolation has three parts, and it matters which protects what (LP1-03, finding F06):

| Layer | Where | What it protects |
| --- | --- | --- |
| **Primary — the API** | The global guard computes `accessibleSubsidiaryIds` (`super_admin` and `standard_user`: their grants, intersected with their own organisation; `masterkey` and `auditor`: their organisation) and a standard user's `categoryGrants`; every service scopes its queries by them, activity records through the one record-scope rule | **The API's queries.** Nothing else filters them: the API connects as `tonyai_runtime`, which bypasses RLS. `apps/api/test/int/tenant-isolation.int.spec.ts` sends another organisation's ids to every tenant route, as all four roles, through the real application, and requires the same answer as for an id that does not exist — the reporting-context routes included, where another organisation's subsidiary as the selection answers empty with the context echoed, and an export with the same compared headers and file name (but for the selection's 8-character id prefix) and the same generation audit contents — its generated id and time aside — but for the selection it records |
| **Database invariants** | Composite foreign keys on `user_subsidiary_access`; the runtime role's privileges | A grant can only join a profile and a subsidiary of the **same organisation**, whoever writes it (API, seed, service role, owner) — short of a session in replica mode, as a restore runs, which skips foreign-key triggers; `runtime-role.mjs check` scans the data for that. The runtime role cannot alter policies or the schema, cannot rewrite or delete `audit_log`, cannot read `_prisma_migrations`, can create a profile only with the columns an invitation sets and change only its `role`, UI language and enabled state (and the Auth and reset bookkeeping beside it) — never its organisation (D17) — cannot move a subsidiary to another organisation, and holds SELECT, INSERT and DELETE on `user_subsidiary_access` with UPDATE on its `categories` column alone (a grant's keys are insert-and-delete only) |
| **Defense‑in‑depth — RLS** | Supabase **RLS** policies (`auth.uid()`‑keyed, SELECT-only) | **Direct database clients** (PostgREST with a user's JWT or the anon key). Every policy's explicit-grant branch also requires the same organisation, independently of the keys. RLS does **not** filter the API's queries, so it is not a second line behind a service that forgot its tenant predicate — the integration test above is |

**The sixteen role-keyed policies** (migration `20261125180000_inc26_roles_approval_chain`, which restated all of them with `ALTER POLICY` in the transaction that renamed the roles; all SELECT-only, none `FORCE`d). The fifteen tenant policies — on `subsidiaries`, `locations`, `period_locks`, `targets`, `subsidiary_denominators`, `evidence`, `activity_records`, `activity_record_evidence`, `import_batches`, `inventory_boundaries`, `inventory_boundary_subsidiaries`, `inventory_boundary_sites`, `inventory_attribution_policies`, `inventory_applicability_cells` and `inventory_sources` — share one shape: an **organisation-wide branch** for a profile whose role is `IN ('masterkey','auditor')` in the row's organisation, OR a **grant branch** through `user_subsidiary_access` (the holder's grant for the row's company, same organisation). On thirteen of them the grant branch is unchanged, since their rows carry no category. On **`activity_records_select_scoped`** and **`activity_record_evidence_select_scoped`** the grant branch adds the category condition: the holder's role is `super_admin` (`p.role = 'super_admin'`), or the record's category is in the grant's `categories`, or the record (for the evidence link, the linked record) was created by the holder. The clause names the role that passes whole, not the one that is narrowed, so it **fails closed**: a role added later is narrowed until a migration names it. `import_batches_select_scoped` has no grant branch of that shape: past the organisation-wide branch it admits a batch's uploader while every company the batch names is still granted to them. The sixteenth, **`audit_log_select_scoped`**, admits a profile whose role is `IN ('masterkey','auditor')`, for its own organisation's rows only. A `super_admin` reading the audit log directly gets no row. `pnpm rls:probe` proves each branch as the four roles in two organisations.

**Three database credentials.** `DATABASE_URL` is the least‑privileged **runtime role** `tonyai_runtime` — the API, its Storage sweeper, `storage:reconcile` and `anomaly:recompute`. It owns nothing; its exact privileges are listed (and checked) in [`packages/db/scripts/runtime-role.mjs`](../../packages/db/scripts/runtime-role.mjs): no DDL, no TRUNCATE, `audit_log` INSERT/SELECT only, on `organisations` SELECT and a column-level INSERT (self-service registration: an organisation is created, never changed, offboarded or deleted at runtime), nothing on `_prisma_migrations`, **no USAGE on Supabase's `storage` schema** — it reads Storage's catalogue (`storage.objects`) only through two pinned SECURITY DEFINER readers in `public`, `storage_catalogue_page` and `storage_catalogue_has` (`storage:reconcile`'s orphan and missing-object scans), because Storage's own SECURITY DEFINER helpers pin no `search_path` and ran a caller's temporary type as `supabase_storage_admin` — and **BYPASSRLS** — the API acts for every tenant and the sweeper's owned‑bytes guard must see every row. `DIRECT_URL` is the **owner** (`postgres`), used only by migrations, DDL, the seed and operator tooling. A migration creates the role without a password; `pnpm setup` generates a random local one (kept only in the `.env` files, re-generated on every run) and sets it as a SCRAM verifier, so the password never reaches the server's logs; the integration suite and CI generate their own, while `pnpm docker:up` reuses the saved local runtime password when available; a deployed environment's operator sets its own with psql's `\password`. The provisioning refuses any database that is not plainly local — a loopback host and no connection parameter that could redirect it (Prisma honours `?host=` over the URL's host); that is an accident guard, not proof of locality — a port forwarded to a deployed database looks local, so local tooling (`pnpm setup`, `test:int`, `e2e`) is never run through one. `node packages/db/scripts/runtime-role.mjs check` verifies, read-only, in any database: the role's privileges and attributes, that no grant in the data crosses an organisation, that no role but its owner holds a table-level verb (TRIGGER, TRUNCATE, REFERENCES, MAINTAIN) on, or may EXECUTE, anything in `public` — now or by default privilege, so a function a migration adds is born executable by its owner alone — that every SECURITY DEFINER function the runtime role or the factor loader can set running — by calling it, by writing a table a trigger of it guards, or by DDL an event trigger of it watches (a temporary object is DDL) — pins its `search_path` with `pg_temp` last, a reviewed platform body excepted while it is unchanged (pg_graphql's `increment_schema_version`), and — as warnings — what the role reaches only because the platform grants it to PUBLIC (locally Supabase's `pg_net` request queue) and another creator's (Supabase's `supabase_admin`) default privileges in `public`. Local container startup provisions against `DIRECT_URL` before passing only the runtime URL into the API; compose rewrites its host to `host.docker.internal`. When the sourced `DATABASE_URL` already contains a loopback `tonyai_runtime` login, startup reuses its password and provisions it idempotently; host dev, integration and maintenance commands keep working with their saved credentials. A fresh random password is generated only when no reusable local runtime credential exists. `pnpm docker:down` does not rotate it. A new table needs a runtime grant in its migration and must be added to that file's privilege list — the integration suite and `rls:probe` fail until it is. A third login, `FACTOR_LOADER_DATABASE_URL`, is the factor library's loader **`tonyai_factor_loader`** (LP4-02): no BYPASSRLS (policies of its own admit it), SELECT and INSERT on the three library tables and UPDATE of a release's seal and withdrawal columns, nothing else; the only writer of the library besides the owner — the service role keeps SELECT there and nothing more, and `runtime-role.mjs check` names any other writer, any client that can act as the loader, and a loader that could set `session_replication_role`. Its login is provisioned like the runtime's (`runtime-role.mjs provision-loader` locally, `\password` in a deployed environment, where it never reaches the API's environment and the role goes back to `NOLOGIN` between loads); the integration suite provisions its own. **Never `FORCE` RLS**: it would not filter the runtime role's queries in any useful way (they carry no user context) and would break the owner's.

**Role and access changes** go through one boundary, `AccessAdminService` (`apps/api/src/auth/access-admin.service.ts`; routes under `/users`, LP4-01): a `masterkey`, or within its own companies a `super_admin`, of the organisation — each action by its own rule (see [Who administers whom](#account-lifecycle-lp4-01)) — never across organisations, never on their own role or their own account, serialised per organisation with the actor re-read (a disabled or demoted administrator, or a `super_admin` whose grant was withdrawn, is refused), and audited in the same transaction. That includes creating an invited account, replacing a granted account's companies and categories, and disabling or enabling an account. There is no platform-wide administrator role; organisations and their first administrators are provisioned by the operator or, where an environment enables it, created by code-gated self-service registration (decision D18 as amended 2026-11-11) — see [Account lifecycle](#account-lifecycle-lp4-01).

Additional guarantees:

- **Token verification** — Supabase access tokens are accepted under both signing schemes: the legacy shared **HS256** secret and **asymmetric** keys (ES256/RS256) fetched from the project's JWKS. The key material fixes the algorithm allow‑list on each path, so a token can never downgrade a public key into an HMAC secret, and `alg: none` matches neither path. Tokens must carry `aud: authenticated`, `sub` and `exp`, which is what keeps the anon/service‑role keys (JWTs signed with the same secret) from being replayed as user tokens, and this project's issuer in `iss` — the key proves who signed, not for which project, so a correctly signed token from another Auth server sharing the secret or key set (a second environment, a copied `.env`) is refused. The issuer defaults to the origin of `SUPABASE_URL` + `/auth/v1`, what GoTrue stamps on a hosted project and on the local CLI (`http://127.0.0.1:54321/auth/v1`); `SUPABASE_JWT_ISSUER` replaces it exactly where the API reaches Auth through another address (a self-hosted project behind a private hostname). A correctly signed token with a wrong issuer — or a user token with none — is logged as a configuration error, at most once per five minutes per kind — producing one needs the signing key, and it means either the expected issuer is wrong or another Auth server shares the secret or key set (rotate it) — while the client gets the same 401. `SUPABASE_JWT_SCHEME` pins the accepted scheme; a boot-time check **refuses to start** with an unpinned scheme, the public demo secret, a `SUPABASE_JWT_ISSUER` that is not an exact printable-ASCII http(s) URL without credentials, or no determinable issuer. The issuer checks hold everywhere; the scheme and demo-secret checks are on by default and are relaxed only by an explicit `ALLOW_INSECURE_LOCAL_AUTH=true` **together with** a loopback `SUPABASE_URL` — deliberately not keyed on `NODE_ENV`, since the container image sets it locally and a plain `node dist/main.js` deployment sets nothing, so a copied `.env` pointed at a real project always fails closed.
- **RBAC** — reads are scoped for everyone (the whole organisation for a `masterkey` and an `auditor`, granted companies for a `super_admin` and a `standard_user`, and ticked categories on top for a standard user's activity records); writes are split by capability, never by a role literal in a service (see the request lifecycle above and the [roles table](data-model.md#roles-rbac)). Who decides a record is routed by its author's role, and **nobody but a masterkey decides a record they created** — see [Record lifecycle: who decides a record](#record-lifecycle-who-decides-a-record). **Only a record's author edits it, submits it or recalls it** (decision D02; BUG-R2-03, decision 2026-11-10 (fourth)), whatever their role, a masterkey included: without this, an approver could change a colleague's figure and then approve it, which the self-approval rule alone cannot see. **A record's evidence is the author's too** (Decisions 2026-11-12): uploading, detaching or deleting a file is refused to anyone but the author of every record concerned, a masterkey included — otherwise an approver could re-file a colleague's draft and then approve it. Deleting a draft or rejected record stays open to its author and to a `masterkey`; a `super_admin` deletes only a record it created. Void, period lock and unlock, and organisation structure stay the masterkey's alone; an `auditor` changes nothing but its own language, theme and password.
- **Lifecycle integrity (LP1-01)** — every write to an activity record, its evidence links or a period lock follows one protocol (`apps/api/src/activity-records/lifecycle-lock.ts`): a transaction-scoped advisory lock per reporting period (shared for record and evidence writers, exclusive for lock/unlock — so even a period with no lock row serialises a create against a lock), then `FOR UPDATE` row locks (records, then evidence files, each in key order), every gate re-checked against the locked row, and the change written **with its audit row through the same transaction** — neither commits without the other. A request that was valid against what it read, but lost a race to another writer, gets a **409 "This record was changed by someone else… Reload it and try again."** (`RecordChangedError`); nothing was written and the server never retries on its behalf. Evidence rows are deleted inside the transaction and their Storage objects only after it commits — through a `delete` intent that commits with them (LP1-02, below).
- **Recoverable Storage effects (LP1-02)** — Storage has no transaction, so every object an API path writes or removes is first named in `storage_intents` (`apps/api/src/storage/storage-intents.service.ts`). An **upload** commits an `upload` intent before sending the bytes; the transaction that writes the owning row (evidence, an import batch, or a report issuance) deletes it — as its first statement — in the same commit. If that transaction fails the intent becomes a delete and the object is removed — but only while the intent is still there, so a transaction that committed although its acknowledgement was lost keeps its bytes. A failure *before* that transaction began — an upload that reports a failure (evidence, an import's source file, a report PDF), or the issuance's read-back of its PDF — cannot have a committed owner, so its object is removed even when the sweeper took the intent while the bytes were on their way (`abandonUnadoptedUpload`). A **removal** (detach of a file's last link, `DELETE /evidence/:id`, a record delete) writes a `delete` intent with the row delete and its audit row, and removes the object after the commit. An object that already has a pending `delete` gets that intent reset (due now) rather than a second one, and a sweep closes an intent only under the lease it took — so bytes that land after a removal stay named. Whatever fails — the database, Storage, the process — leaves an intent that the in-process **sweeper** retries: every `STORAGE_SWEEP_INTERVAL_SECONDS` (default 300; `0` turns it off), at most 100 intents a pass, by lease (`claimed_until`, `SKIP LOCKED`) so replicas never remove the same object twice and no transaction is held across a Storage call, with exponential backoff (30 s doubling to 6 h, never giving up). An upload intent is abandoned only after 15 minutes. **Bytes a row still owns are never removed**, whatever an intent says, and objects are written with `upsert: false`, so nothing overwrites existing evidence. **`STORAGE_CLEANUP_HOLD=1` stops every removal** — set it while a backup or restore runs: intents wait, nothing is lost. The sweeper never removes an orphan (an object no row owns and no intent names) on its own: after a database restore such an object may be the only copy of a file the restored database no longer remembers. `pnpm storage:reconcile` reports orphans, rows whose object is missing, hash mismatches and stuck intents; it removes orphans only with `--reclaim-orphans --apply`, older than 7 days by default, and never under the hold. **Removal fails closed under a database role that RLS filters** — the owned-bytes guard is only as good as the rows it can see, so the sweeper hands its intents back and the CLI refuses to run unless the role bypasses RLS on `evidence`, `import_batches`, `report_issuances` and `storage.objects` (the owner role does; LP1-03's runtime role must). **After a database restore:** set `STORAGE_CLEANUP_HOLD=1` on every API process *and* in the shell running the tool (it is per process), run `pnpm storage:reconcile --forget-uploads` — upload intents restored from the restore point name bytes committed later, in the history the restore discarded, so they become reported orphans instead of being abandoned and removed — then `--verify`, and lift the hold only after reading the report.
- **Audit immutability** — `audit_log` has a SELECT‑only policy (`masterkey` and `auditor`, own organisation) and **no** UPDATE/DELETE; it is append‑only, and the runtime role holds only INSERT and SELECT on it (LP1-03). The role-model migration ran only INSERT on it (one `role_model_change` row per carried account); no row was rewritten.
- **Who reads audit** — the organisation-wide `GET /audit` (and its RLS policy) is read by a `masterkey` and an `auditor` (`can(role, 'audit.read')`, INC-2.6 §6, ruling R4); a `super_admin` reads the trail of each record in its companies instead. One record's history, `GET /activity-records/:id/audit-trail` (WP5, INC-2.6 §6), is read by a `masterkey`, an `auditor` and a `super_admin` for any record they can read (`record_trail.read_any`) and by a `standard_user` only for a record they created (`mayReadRecordTrail` in shared-types, read by the API and the web). A role stored on a row older than the organisation's `role_model_changed_at` is shown under the earlier role model's name (`displayRole`: an earlier `super_admin` as `legacy_super_admin`), so history never shows today's scoped role for the earlier organisation-wide one. The API runs as the runtime role, which bypasses RLS, so `RecordAuditTrailService` is the whole confinement: the record is loaded through the same scoped read as `GET /:id` (another organisation or a subsidiary without a grant answers exactly as that read does), the audit query is keyed by the record and the caller's organisation, actor names are resolved within the organisation, and the answer is built from an allow-list (`buildRecordTrail`): kinds, times, names and stored roles, reasons, submission numbers and field values. It never returns stored audit JSON, a calculation snapshot, a user id or an email address, and reading writes nothing.
- **Bounded input** — every free‑text column a write DTO accepts is length‑capped from one constant in `@tonyai/shared-types`: `periodValue` (records *and* period locks), `activityUnit` (records *and* the calculation preview), `varianceReason` (sharing `EXPLANATION_MAX_LENGTH` with the void reason and the reviewer's note — three explanations about a figure, one number), and all six subsidiary descriptors. All of them are unbounded `text` in Postgres and all of them reach a generated PDF, Excel sheet and CSV cell verbatim. The caps are app‑side only and deliberately so: `@MaxLength` counts Unicode code points while a Postgres `varchar(n)` counts them differently again, so a database bound would turn a would‑be 400 into a 500. Groundwork for bulk upload, where the multi‑megabyte cell actually arrives. A cap bounds how much padding can be stored, not whether it is stored, so `activityUnit` is also **whitespace‑normalised before it is bounded** (`storableUnit`): one plain space per run, matching the `\s` class `canonicalUnit` itself uses. The vocabulary trims AND collapses `\s+` to `_` before it looks a unit up, so a run does not have to vanish to be ignored — it maps onto the `_` of a multi‑word key. `us`, a **carriage return** and `gallons` was a valid ten‑character `us_gallons`, far under the cap, stored as sent into the column, the immutable snapshot's `inputUnit`, the audit row and all three exports; LF, TAB, VT, FF, U+2028, U+00A0 and U+FEFF behave the same, interior or not, and #111's derived aliases brought `kw`+CR+`h` down to four characters. Case and alias are resolved once, **at the write**: `activity_records.activity_unit` stores the vocabulary's canonical value (`kWh`, `MWh`, `cubic_metres`, …) via `storedUnit`, while the calculation snapshot keeps the entered spelling as `inputUnit` until the record is next edited — so `kw h`, `KWH` and `MWH` are one unit to every export and `GROUP BY`, `unitSymbol` never falls back to raw text, and the U+212A KELVIN SIGN homoglyph can no longer reach the column. A hand‑written migration (`20260917210000_canonical_stored_unit`) brings rows stored before the rule onto it without touching their snapshots.
- **Caller text is cleaned where the API stores it, and named where it quotes it** — an upload's filename, the header cells an import refusal quotes, and every sentence that repeats a value back (the import report's cell refusals, the unit and period refusals, the calc engine's unit sentences, so the single-record API is covered too) pass through one rule in `apps/api/src/common/caller-text.ts`. It drops control characters and unpaired surrogates (Postgres refuses U+0000 inside `jsonb`, and half a surrogate pair fails the write too), the line and paragraph separators U+2028/U+2029, every format character except ZWJ, ZWNJ and the prepended concatenation marks that are drawn (U+0600-U+0605, U+06DD, U+070F, U+0890, U+0891, U+08E2, U+110BD, U+110CD), and the code points Unicode reserves as invisible but has not assigned. That takes the bidi controls and marks, the zero-width space and the word joiner, the invisible operators, and the tag characters, which spell out ASCII nobody sees. Text that is STORED (`sanitiseCallerText`: the filename and a refusal's reason, the only caller text the append-only `audit_log` holds) keeps everything else and is bounded in code points, so a cut never lands inside a character. A sentence instead QUOTES a value through `quoteCallerText`, which NAMES every character it cannot show — the dropped ones, the invisible ones the rule keeps (a variation selector, ZWJ), U+2800, and the `<`, `…` and `"` its own syntax is made of, so a file cannot forge one — writing each run in place: `Unrecognised column(s): "category<U+200B>", "<U+2063 x40>tco2e". Expected: …`. Naming rather than cleaning matters because the value is matched as written: a quote cleaned in silence named a column the file got right, and told a user their unit was `cubicmetres` when the cell held a BOM and a tab. Each quote is delimited and bounded twice — in units (a character or a whole marker, so padding cannot push a value out) and in code points (so the longest possible refusal still fits an audit row whole). A `$` is dropped from what the unit refusal quotes, because class-validator replaces `$value` in a finished message with the raw value as a `String.replace` replacement string: a 99,994-byte unit of `$value` tokens came back as an 18,563,231-byte 400. The import report bounds every message at `BULK_UPLOAD_MESSAGE_MAX_LENGTH` as well, after the failure has been classified by its raw text; before that, one XLSX shared string behind a thousand rows turned a 12,416-byte workbook into a 32,092,008-byte report, and the same file now returns 135,008 bytes. The issue count needs no cap of its own: each row is accepted or refused once, so the row cap bounds it.
- **No secrets in git** — all `.env*` files are git‑ignored; only `.env.example` templates are committed.

**Web response headers** (`apps/web/security-headers.mjs`). Every response, redirects included, carries nosniff, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, a permissions policy matching the API's and, in a production image, HSTS as the API sets it; `X-Powered-By` is off. `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin` join them (`pre-g5-security-hardening`). The CSP is one enforced policy: the structural directives (`frame-ancestors`, `base-uri`, `object-src`, `form-action`) and the resource directives (`default-src`, `script-src`, `style-src`, `img-src`, `font-src`, `connect-src`) together; nothing is report-only since `pre-g5-security-hardening`. `connect-src` is fixed at build from the `NEXT_PUBLIC_*` values, so an image's policy names that image's hosts. `script-src` and `style-src` keep `'unsafe-inline'`: Next's inline bootstrap and the chart's injected style need it until a nonce pipeline exists (Open questions). Violations go through `report-uri` to the API's public `POST /api/v1/security/csp-reports`, which answers 204, reads at most 16 KiB and 10 reports a body, allows 30 bodies a minute per client address (taken at admission, before the body is read, and apart from that address's quota for every other route), and logs each report as one `csp_violation` warning: directive, blocked origin, page path and disposition, never a query string or fragment, and only values a browser could send (a directive name, `enforce` or `report`, a web origin, a scheme or a keyword; anything else is `unknown`). Any media type but the three is 415, a form included. Nothing is stored. No `report-to`: with it, Chrome ignores `report-uri` and queues the report in its Reporting API, which headless Chrome did not deliver within 100 s (measured). The API's own responses carry `Cross-Origin-Resource-Policy: same-site`, CORS preflights included.

### Record lifecycle: who decides a record

OpenSpec `inc26-roles-approval-chain` (INC-2.6 §1.1, design Decision 7, owner rulings R1 and R3).

- **The approval chain.** A pending (`submitted` or `under_review`) record has one approver, worked out by `recordApprover` in `@tonyai/shared-types` from the author's **current** role, never stored: an active `masterkey`'s record is decided by that masterkey alone (`author`); an active `super_admin`'s record by a `masterkey`; anyone else's (a `standard_user`'s, an `auditor`'s, a disabled account's of any role, a profile that is gone) by a `super_admin` granted the record's company.
- **The fallback.** When a record would go to a `super_admin` and the company has no **active** one — the role, a grant for the company, `disabled_at` null, and an accepted invitation (or none, for a seeded or provisioned account) — a `masterkey` decides it. The rule is evaluated when the decision is made, not at submission.
- **Enforced inside the record's lock.** `startReview`, `reject` and `approve` call `assertRecordApprover` inside `withLockedRecord`, after the re-gate and the submission check; it re-reads, in the decision's own transaction, the decider's role, disabled state and grant, the author's role and disabled state, and the company's active super_admins, so a role or grant changed since the request was authenticated cannot be used. Refusal order: the role gate (403, only a `masterkey` or a `super_admin` decides), `record_changed` (409), a scoped decider no longer granted the company (404, as an unknown record), `self_review_forbidden` or `self_approval_forbidden` (403, the author is not a masterkey — whatever role they held when they created the record), then **`not_record_approver`** (403, `params.approver` = `super_admin`, `masterkey` or `author`). A decision is not serialised against access administration: each is valid on the state it read, and the worst outcome is a fallback approval the document allows.
- **Self-approval.** A masterkey takes into review, returns and approves its own record; nobody else decides it while its author is an active masterkey. That approval is written with the audit action **`self_approve`** (not `approve`), with the approval's diff, and shown in the record trail as the kind `self_approved`. No stored column marks it: the reviewer equals the author on an approved record.
- **On reads.** The record read and the list attach `approver` to every `submitted` or `under_review` record (null on every other status), with one query for the page's authors and one for its companies. The review queue's default view, `awaitingMyDecision=true`, is a database filter built from the same two facts, so paging stays correct.
- **What stays the masterkey's.** Void, deleting a colleague's draft or returned record, and copying a voided record of another author. Decision rights give no void right.

### A standard user's category scope

OpenSpec `inc26-roles-approval-chain` (INC-2.6 §1, §7.3, ruling R5, design Decision 6).

- **What is refused.** A `standard_user` creates, edits (checked on the category the record would hold after the edit), submits and bulk-uploads a record only when its category is ticked on the user's grant for the record's company; otherwise **`category_not_granted`** (403, `params.category`), after the role and scope checks, with nothing changed (in a bulk upload, a row error of that code, in the dry run and the apply alike). Recall and delete are not gated: they only take data back. A `masterkey` and a `super_admin` are never limited by category.
- **What is hidden.** One helper, `recordScopeWhere` (`apps/api/src/activity-records/record-scope.ts`, with `recordScopeSql` for raw SQL and `inRecordScope` in memory), is the only source of the activity-record filter: a company in scope for three roles; for a standard user, per grant, the company **and** a ticked category. Every read of activity records takes it — the record list and read, the emissions summary, completeness and tracking matrix (so target progress and intensity, which read through them), evidence through its record, and import batches. A record outside it answers exactly as one that does not exist (404). Reads not keyed by category (facilities, period locks, targets, the boundary) stay company-scoped; reports and datasets are refused to a standard user.
- **The own-record rule.** A record the user created stays readable to them, whatever its category, so a withdrawn category never orphans a draft: its author still reads, recalls or deletes it. A file the user uploaded stays readable to them too.
- **Direct clients.** The grant branch of `activity_records_select_scoped` and `activity_record_evidence_select_scoped` carries the same condition (see the sixteen policies above).

### Account lifecycle (LP4-01)

Decisions 2026-10-10 (second), K3–K6, and their sub-decisions S1–S12 (the planning file).

- **Who administers whom (INC-2.6 §6; OpenSpec `inc26-roles-approval-chain`, design Decision 9).** A `masterkey` invites `super_admin`s (with their companies, no categories) and `auditor`s, sets a super_admin's companies, changes any other account's role to `super_admin`, `standard_user` or `auditor`, and disables or enables any other account; it does not invite a standard user or set one's company and categories (ruling R3). A `super_admin` invites `standard_user`s and sets their company and categories, only inside its own companies; it changes no role and disables no one. **Nobody is made a `masterkey` in the product** (ruling R1): an invitation or role change naming it is refused 403 for every actor, and a masterkey comes only from registration, the operator's `provision` or the carry-over. Invitable roles, assignable targets and role-change targets are `INVITABLE_ROLES`, `ACCESS_ASSIGNABLE_ROLES` and `ROLE_CHANGE_TARGETS` in shared-types. A grant (or a category) for an organisation-wide role, or a category for a super_admin's grant, is refused `access_role_mismatch` (409). **One company per standard user** (ruling R6): an invitation naming two, or a change that adds a company and would leave the user holding more than one — counted over all their grants, those the actor cannot see included — is refused `standard_user_single_company` (409); withdrawals and category changes always pass, so an account carried over with several companies is edited down, never up. A super_admin's access change is a diff inside its own companies: grants outside are neither returned to it nor touched, and a company outside answers `subsidiary_not_found` (404) like an unknown one. A role change withdraws every grant the account holds in the same transaction, whatever the roles, each withdrawal audited. Every grant added or withdrawn and every categories change writes its own audit row (categories before and after); an unchanged save writes none. The users list follows the same rule: a masterkey lists every account, a super_admin the standard users with a grant in one of its companies or with no grant at all (so one whose last grant was withdrawn is never stranded), seeing only the grants inside its own companies.
- **Provisioning (D18, as amended 2026-11-11).** An organisation and its first `masterkey` come from two places only: the operator's CLI, and — where an environment enables it — self-service registration (next item). The operator runs `pnpm onboarding provision` (Scripts) on the owner's connection, which creates the organisation, its default subsidiary, and its first `masterkey` and sends the invitation — audited with a null `userId` and the operator's address in `diff.operator`, a dry run unless `--apply` (which says whether a re-run would re-send); a re-run completes what failed and changes nothing that is already right, except that an unaccepted invitation is sent again with a fresh link. `--organisation-id` adds a first administrator to an existing organisation (one whose administrators have all left) and creates no subsidiary. **Every new organisation is born with one default subsidiary** (UAT round 2, K1; OpenSpec `uat2-standalone-default-subsidiary`): the company itself — its legal name, and the operator's trading name and sector — in the organisation's geography, Scope 1 and 2, tracked at subsidiary level, with no facility, no grant and no inventory-boundary entry, so its administrator can add a facility or a record at once; afterwards it is an ordinary subsidiary, renamed, edited or deleted under the usual rules. Its audit row has no actor, names the source and `default: true`, and leaves the names out. Provisioning a new organisation refuses a `--geography-code` other than `UK`, `TR` or `EU` before writing anything, since its subsidiary could have no other. Organisations created before this shipped were not given one (owner, 2026-11-12). Re-run, `provision` also re-sends an invitation that went out but was not accepted (the first administrator has nobody else to ask).
- **Self-service registration (owner decisions 2026-11-11; OpenSpec `self-service-registration`).** `/register` → `POST /auth/registration` is the one HTTP surface that creates an organisation, and it is **off unless the environment sets `REGISTRATION_CODE`** — exactly five letters or digits, case-sensitive, a Key Vault secret shared by hand with invited companies; without it both routes answer 404 `registration_unavailable` (a guard, so before any body is validated). The sign-in page links to `/register` (a path on the same web app, never a hostname) only while the public `GET /auth/registration` answers with a status; where registration is off, or that answer cannot be read, the page shows no link and no message, and signing in never waits on it (OpenSpec `login-register-link`). **On a hosted environment the code arrives only through the release** (OpenSpec `registration-hosted-config`): an optional `registration` block names the exact version of the `registration-code` secret, which the API alone references — never a value in a manifest, a Terraform variable, a plan or a log — and the API identity may read it only once the foundation's `registration_secret_ready` grant is applied; the owner's secret tool stores only a code of the shape the API accepts; the deploy readback fails on a registration secret or setting the release does not name, on any difference from it, and on any registration setting on the web app. The code is kept as a digest and compared in constant time. A wrong code — any wrong shape included — is refused in words (403 `registration_code_invalid`: the code says nothing about any address), logged with a running count and never the code tried, and spends the client address's `AUTH_EMAIL_PER_IP_PER_MINUTE` quota, which the password reset shares; five characters are guessable by a caller with many addresses, which is accepted for a hand-shared code — a guessed code yields organisations holding nothing but their own default subsidiary, and invitation emails, never another tenant's data — and answered by rotating the secret. Past the code the answer is **202 with no body for every address** and the work runs after the response on a bounded queue (200, two workers), so neither body nor timing says whether an address has an account. For a new address, `AccessAdminService.registerOrganisation` writes — in one transaction on the runtime role — the organisation (the company name as its legal name; country `TR`, geography `TR`, currency `TRY`), its default subsidiary (named by the company, as in Provisioning above; its runtime write is the role's existing INSERT on `subsidiaries`), its `masterkey` profile with the job title, the invitation (no inviter) and a `consents` row naming the KVKK notice version shown, each audited with a null `userId`, `diff.source` `auth:registration`, and no name, address, job title or company; the invitation is then delivered as any other, in the form's language, with wording of its own that **carries nothing the registrant typed** — no name and no company: the form is public and the address may not be its typist's, so typed text never rides in an email from this domain. The same holds for a password reset requested before the invitation is accepted: it greets nobody (the reset is public too, so a registration followed by a reset would otherwise carry the typed name). The address must be one Supabase Auth accepts — an unquoted ASCII local part and ASCII domain labels (measured against Auth) — since Auth refuses any other only after the organisation would exist, with an administrator no email reaches. Submitted again for a registered address whose invitation is not accepted, that invitation goes out again with a fresh link, at most once per five minutes (claimed in one statement) and **five emails in all** — past that the registrant uses "forgot password", which opens an unaccepted account too; for any other address — active, disabled, offboarded, invited by an administrator or provisioned by the operator — nothing happens: registration never re-sends an invitation it did not create, since a fresh link voids the previous one. Two companies with the same name are two organisations, each with its own subsidiary; a re-submission creates neither. The runtime role's new reach is a column-level INSERT on `organisations` (name, country, geography, currency — never `offboarded_at`, no UPDATE, no DELETE). **The KVKK notice shipped today is a placeholder**, labelled so on the page: with a code set the API refuses to start unless `REGISTRATION_ALLOW_PLACEHOLDER_CONSENT=true`, which only an environment where no real customer registers sets (local, QA) — on hosted environments the release carries that allowance, and a release that turns it on for anything but `staging` is refused by the manifest validation and again by Terraform — the pilot cannot open registration before the reviewed notice ships under a new `REGISTRATION_CONSENT_VERSION`. An unaccepted registration leaves its organisation in place; the operator's `offboard` closes one. **Known limits, accepted for a code shared by hand (security review 2026-11-11; Open questions, "Self-service registration follow-ups"):** (a) *address squatting* — a code holder who registers someone else's address gains no access (the link goes to the address), but that address then has a profile: its real organisation's administrator is refused `email_unavailable` when inviting it (D17), a later registration by its owner re-sends the squatter's invitation instead of creating theirs, and `offboard` does not free it — only the owner's connection can remove the rows; (b) *the endpoint keeps the secret, the feature does not* — "no existence oracle" holds for `POST /auth/registration`, but anyone who completes a registration is a `masterkey`, and `POST /users/invitations` answers `email_unavailable` for any address with a profile. D17 makes the answer unavoidable, so it is bounded and audited, an accepted risk (`pre-g5-security-hardening`, owner decision 2026-11-24): every refusal writes an `invite_refused` row for the inviting organisation, without the address. Five within an hour refuse every further invitation from that organisation with 429 `invite_refusals_exhausted` (with `Retry-After`), before the address is looked up, until the oldest ages out. What remains: five answers an hour per organisation, more through more registrations, which the code and its per-address quota bound; invitations to *new* addresses stay bounded only by the WRITE quota, and each sends an email and holds that address platform-wide (address squatting, (a) above); and the delivery-time `email_unavailable` for an Auth user with no profile, recorded on the invitation and not counted; (c) the per-address quota is held in memory per API replica, and a full queue (200) drops a registration behind the same 202. Supabase's own public sign-up stays off: the Auth user is created through the admin API, as for an invitation.
- **Invitation, the database first (K4, S1–S3).** A `masterkey` or a `super_admin` invites from `/users` (by the rule of "Who administers whom" above): one transaction on the runtime role creates the profile (its id chosen there), its grants and an `invitations` row (`pending`), with the audit rows — never the address or the name in a diff. Only then does the API create the Supabase Auth user with that same id, mint an invitation link (`auth.admin.generateLink`) and email it; each attempt is counted on the invitation and its outcome recorded (`sent`, or `last_error_step` `auth`/`email` with a short code such as `smtp_failed` or `mail_not_configured`). The users screen shows a failed delivery and its **Re-send** retries every step — a re-minted link voids the last one. One account per address across the platform (D17): an address with a profile anywhere answers `email_unavailable`, audited as `invite_refused` and bounded to five an hour per organisation (known limit (b) above). Addresses are stored trimmed and lower-case (CHECK `profiles_email_normalised`) and looked up by exact equality, so `%` and `_` in an address are characters, never wildcards over other accounts; an invitation's subsidiaries are checked before its address.
- **Company access on the users screen (BUG-R2-01 and BUG-14; OpenSpec `uat2-user-access-clarity`, `inc26-roles-approval-chain`, capability `access-roles`).** Grants mean something for a `super_admin` (any number of companies, every category) and a `standard_user` (one company, with the categories ticked for it); a `masterkey` and an `auditor` read the whole parent company and hold none. `/users` names a granted account's companies in the access column (in name order, three at most, then "+N more"; the full list on the row) and marks one with no grant as "None granted"; a masterkey or auditor row reads "Whole parent company". "Edit access" is a button in the access cell of each row whose access the reader may set — for a masterkey the super_admin rows, for a super_admin the standard user rows — not only a menu item. The picker it opens, shared with the invitation, lists only the companies its user may assign: for a super_admin it counts the selection, selects all or clears; for a standard user it allows one company and shows that company's category checklist (an account carried over with several companies shows them as held and removable, with no further company addable). It warns — without refusing — when no company, or for a standard user no category, is ticked, since the API accepts both. The invite dialog offers a masterkey Super Admin and Auditor, a super_admin Standard User alone, and never Masterkey; a role change to Super Admin opens the access editor at once, and one to Standard User says that a super_admin assigns the user's company and categories, because `setRole` grants nothing. Role and grants stay two audited calls. (Until 2026-11-25 only the earlier `data_entry` role held grants; history.)
- **Acceptance.** The email links straight to the web app's `/auth/confirm?token_hash=…&type=invite` (built on `APP_URL`, never a request's Host). The page runs `verifyOtp` on a **click** — a mail scanner that opens links would otherwise spend the one-time token — strips the token from the address bar and sends no referrer; the invitation is then marked `accepted` (audited as the invitee) and the person chooses a password at `/auth/set-password`. Links expire after Supabase Auth's `otp_expiry`, **1 hour** (S4); an expired invitation is re-sent by an administrator, and a dead link also offers the password reset, which is how someone who stopped before choosing a password gets back in. Acceptance is also retried: the web repeats a transient failure with the token of the session its Auth operation returned (the email link's `verifyOtp`, the sign-in, or the session the set-password screen checked), the same token on every repeat; the browser's shared session is never read again, so another tab's sign-in can neither redirect nor stop it. It runs again after the password is chosen and after every password sign-in, so an acceptance that failed closes later; a page waits for it 5 s at most. After a recovery, Auth is asked to end the other sessions first, before the acceptance, and the screen says when that failed. The API locks the profile row and checks it again inside the acceptance's transaction: an account disabled after the guard read it is refused `account_disabled` and its invitation stays revoked (pre-pilot defects; Codex review of #350).
- **Session inactivity.** After 60 minutes without pointer, keyboard, scrolling or touch activity in any protected tab, the browser clears the session and asks for email and password. Tabs share their last activity through local storage. A protected page checks it before mounting, including on reopening the browser. A missing timestamp requires a fresh sign-in. Supabase Auth measures inactivity from the last token refresh. Its two-hour backstop allows for the one-hour access-token lifetime plus the browser's full idle hour, so a recently active user can return to a hidden tab after the access token expires.
- **Signing out in the web app (pre-pilot defects; Codex review of #350).** Sign out counts as done only when a session read afterwards finds no session and no error: Supabase Auth answers an upstream failure with an error and keeps the session, and with an expired access token it answers a session read with an error and no session while still holding it; then the page stays and says so (`lib/sign-out.ts`). A sign-out that went through clears the signed-in user and the remembered reporting context and leaves with a full navigation, so the page's state and its requests in flight go with it. The root layout's `SessionWatch` follows the session on every page: when it ends for any reason (a sign-out in another tab, a refresh token Auth revoked) or becomes another user's, a page that knew a user (the session this tab last saw, or the loaded profile) goes to sign-in or reloads as the new user, even before its `/me` has answered. Public pages (sign-in, registration, the email-link pages) are left alone.
- **Password reset (K5, S5, S6).** `/forgot-password` → `POST /auth/password-reset` answers **202 with no body for every address**, and the work runs after the response, so neither the body nor the timing says whether an account exists. For an enabled account of an active organisation outside its **5-minute** per-address cooldown (`profiles.recovery_sent_at`, claimed in one statement with its `password_reset` audit row), the API mints a recovery link and emails it in the account's `profiles.language`. Past `AUTH_EMAIL_PER_IP_PER_MINUTE` (default 5) a client address gets 429 — the only 429: accepted requests wait in a bounded queue (1,000) drained by four workers, and one past a full queue is dropped and logged, still answered 202, because whether the queue is full depends on which addresses ahead of it exist (Codex review, finding 4). A worker that finishes looks at the queue again, so a request accepted as the last workers wind down still runs (Codex re-review, finding 3). Once the new password is saved, the set-password screen also signs the account's other sessions out (a client-side, best-effort step; disabling is what revokes sessions server-side).
- **Passwords (S9).** At least **12 characters**, no composition rules (NIST SP 800-63B) — Supabase Auth's `minimum_password_length` and the set-password screen. Public sign-up is off (`[auth] enable_signup = false`): every account starts from an invitation. (`[auth.email] enable_signup` stays on — in this CLI it is the email provider itself, and turning it off refuses every password sign-in.)
- **Setting a password (`pre-g5-security-hardening`; OpenSpec `account-access`).** **The screen:** `/auth/set-password` offers its fields only to a session an email link opened in the same tab within the hour. `/auth/confirm` writes a marker in `sessionStorage` (`tonyai.emailLink`: the verified user, the Auth session the link opened — its `session_id` — the flow and the time) after Auth verified the link; the screen reads it for the session's own user and session when it loads and again when the password is submitted (a later sign-in by the same person in the same tab is another session and finds none), and takes the flow (`invite` or `recovery`) from it, never from the address bar. A signed-in user who opens the page directly, another tab, or a marker over an hour old is told to use their email link and shown no field; while the marker is read no field is shown either; the marker is removed after the save. The password change and, after a recovery, the other sessions' sign-out go through an Auth client bound to the session just checked (in memory, its tokens only), never the browser's shared client, which reads the session again inside each call — so a sign-in in another tab between the check and the call cannot redirect the new password to someone else. This is a screen control, not a server one: anyone holding a session can write the marker or call Auth directly. **The server side** is Auth's own reauthentication (`secure_password_change`, pinned true for hosted by `infra/scripts/auth_settings.py`): a password change from a session created more than 24 hours ago needs the emailed code (measured: 23 h passes, 25 h is refused `reauthentication_needed`), and no email-link flow meets it. Only the owner applies and verifies the hosted setting (`supabase_setup.py --reconcile-auth-only`, a private management readback); the QA auto-deploy, which holds no management token, stops before any change unless the QA variable `QA_AUTH_POLICY_DIGEST` the owner recorded from that run equals the release's policy digest. **The record:** after Auth accepts the password, the web records it with `POST /me/password-set` with the token of the very session the password was changed through, on every repeat, and the API writes one `password_set` audit row as the account, with the flow and a change id the web keeps through its repeats; the row's id is derived from the account and the change, so a repeat, even one overlapping the first try, meets the primary key and writes nothing. Nothing about the password is recorded; bounded and never blocking. The row is the web app's report: any signed-in user can write such a row about themselves, so it shows a password set from the screen, not proof of one. **What remains:** a stolen session under 24 hours old can still change the password through Auth directly. The code mail needs custom SMTP on Supabase Cloud to arrive, and hosted Auth uses Supabase's default English template (an owner follow-up); without it an older session is refused all the same.
- **Disabling (D19, K4, S8).** `POST /users/:id/disable` sets `profiles.disabled_at`, `sessions_revoked_at` and `auth_sync_pending_since` in one audited transaction (an open invitation becomes `revoked`); the guard refuses the account **from its next request** with 401 `account_disabled`, and the web signs it out (`lib/api.ts`). The enable moves `sessions_revoked_at` to its own instant, and every session begun at or before it stays refused — 401 `session_revoked` — whether begun before the disable or while disabled, through a session Auth still honoured (Codex review, finding 1; security re-review P2), and whether or not Auth has caught up: the guard reads when the session began from the token's `amr` sign-in timestamps, which a refresh keeps (its `iat` is the refresh's), so a session that refreshed while Auth still let it is refused too; a new session (a recovery link) is accepted. Then the API bans the Auth user (no refresh, no sign-in) and replaces its password with a random one nobody holds — GoTrue revokes every session on a password change, while a ban alone would bring the old sessions back when it is lifted — and clears the flag — serialised per account, so the last ban or unban to run applies the latest state. Since that call ends every session in Auth, a successful sync also moves `sessions_revoked_at` to it (forward only, and only where a boundary exists): a session begun after an enable's commit with credentials a failed disable left valid loses its API access with its refresh token (Codex re-review, finding 1). Every disable, enable and offboarding moves `auth_sync_generation` on, and a run clears the flag only while the generation it read is unchanged, so an older run never drops a newer change (finding 3). **Auth users are created banned:** for a banned user (a new one always is) or an account disabled meanwhile, delivery arms the flag and lets the same sync apply the profile's state — the unban (before the link is minted), or the ban — never a direct call that could overwrite a newer change (finding 2); an unbanned user of an enabled account is left alone, since the sync replaces the password and an invitee who already confirmed and chose one would lose it. A creation whose answer is lost, or a process that stops right after it, leaves a banned user, never an unbanned one for a disabled account (Codex re-review, finding 2); a failed unban sends no link and records the auth step on the invitation. A failed Auth call leaves the flag set (shown on the users screen) and `pnpm onboarding reconcile` retries it. A re-enabled account signs in again by choosing a new password ("Forgot your password?"); the screen says so. Nobody disables their own account, and the actor is re-read under the organisation's lock, so an organisation always keeps an active `masterkey` (nobody changes their own role, and only a masterkey changes roles or disables accounts). **Residual (Open questions):** a live access token can still read its own organisation through PostgREST until it expires (≤ 1 h) — RLS does not read `disabled_at` (K4); and while Supabase Auth refuses both the disable's and the enable's sync, a session it still honours can set a password of its own and sign in afresh after the enable (the flag shows until `pnpm onboarding reconcile` replaces the password). The boundary relies on Supabase Auth keeping the sign-in's `amr` timestamp across refreshes (measured on GoTrue v2.184.0; without it the guard falls back to `iat`). A session begun in the same whole second as a boundary — a disable, an enable or a sync's password rotation — counts as before it and is refused; a new sign-in is needed (follow-ups (24)).
- **Offboarding (K6, D21).** `pnpm onboarding offboard` sets `organisations.offboarded_at` — the start of D21's 90-day retention clock — disables and bans every member, revokes open invitations and audits each step; the guard also refuses any member of an offboarded organisation. **Nothing is deleted**: the deletion waits for the lawyer (D24).
- **Email transport.** `apps/api/src/mail/`: nodemailer over SMTP, STARTTLS required off loopback; locally the Supabase stack's mailpit (SMTP `54325`, UI http://127.0.0.1:54324), on QA and production Azure Communication Services Email (`smtp.azurecomm.net:587`, STARTTLS, an Entra-bound SMTP Username; decided 2026-10-27). The pilot sends exactly two emails — invitation and password reset (decision 2026-09-27); the invitation has three wordings — invited by an administrator, provisioned by the operator, self-registered — chosen from the invitation's inviter and the registration consent the profile holds.
- **Sender domain and public hosts (LP2-04, hosted QA).**
  - **Sender.** QA sends as `no-reply@tonyai.io`. ACS verifies the root `tonyai.io` as a CustomerManaged domain, so SPF, DKIM ×2 and DMARC pass. A custom sender username exists only once the domain is verified.
  - **DNS.** Google Workspace keeps the root MX and its SPF include. The one root SPF record carries both includes.
  - **Public hosts.** These are `qa.tonyai.io` and `api.qa.tonyai.io`, with free ACA managed certificates. Any host must sit under the parent domain in `infra/config/public-hosts.json`; Terraform, every script and the smoke contract refuse anything else.
  - **Once bound:**

    - `WEB_ORIGIN` (CORS) and the Auth redirect allow-list keep the generated `*.azurecontainerapps.io` web origin as a second entry, because that host still serves.
    - Cookies stay host-only, so users sign in again on the new host.
    - HSTS stays without `includeSubDomains`, so the Google-hosted root is unaffected.

# TonyAI: Data model and roles

> Moved from [`README.md`](../../README.md) on 2026-11-05 (OpenSpec change `refactor-readme`); the text is unchanged.

## Data model

Postgres `public` schema (managed by Prisma); Supabase owns the `auth` schema. `Profile.id` mirrors `auth.users.id`.

| Table | Purpose |
| --- | --- |
| `profiles` | App user: role (`role`, the Postgres enum `"UserRole"` — `masterkey`, `super_admin`, `standard_user`, `auditor`, default `standard_user`; the only column typed with it, see "Roles (RBAC)"), organisation, UI language (`en`/`tr`, CHECK; the runtime may update it — LP3-01) and theme (1:1 with an auth user, same id). LP4-01: `disabled_at` (refused by the guard), `sessions_revoked_at` (set by a disable, an enable and an offboarding; sessions begun at or before it are refused), `auth_sync_pending_since` (Supabase Auth's ban not yet applied), `auth_sync_generation` (moved on by every change the sync must apply) and `recovery_sent_at` (the reset cooldown); `job_title`, the registrant's own (self-service registration; null for an invited or provisioned account, written once and never updated at runtime); created by an invitation through a column-level runtime INSERT |
| `organisations` | The holding company (top of the hierarchy); `offboarded_at` once the operator offboards it (LP4-01, D21); `role_model_changed_at`, the instant its accounts were carried over to the four-role model (`inc26-roles-approval-chain`; set, to the millisecond, for every organisation that existed then, NULL for one created later), which decides how a role stored on an older audit row is shown (see "Roles (RBAC)"). Created by the operator CLI or by self-service registration (country `TR`, geography `TR`, currency `TRY`), each with one default subsidiary in the same transaction (UAT round 2, K1), its tree's root; the runtime role may INSERT one (listed columns) and update only `consolidation_approach` (with `updated_at`), never delete it. `consolidation_approach` (`operational_control` default, or `financial_control`; `equity_share` is announced, not stored): the group's one approach, set by the masterkey and audited (`inc26-group-tree`, see "The group tree") |
| `inventory_boundaries` + `inventory_boundary_subsidiaries`, `inventory_boundary_sites`, `inventory_attribution_policies`, `inventory_applicability_cells`, `inventory_sources` | LP3-04 PR B: an organisation's declared inventory boundary per reporting year, one version per header — declared subsidiaries and sites with their operating months, D11's attribution policies, D12's applicability cells, D05's named sources. Immutable once frozen (`TA014`, every writer), names copied in as it freezes; deleted only with an open version or its organisation; a declared subsidiary or site stays. RLS SELECT-only; clients and the service role SELECT only; the runtime role inserts the rows (never updates one) and deletes only a subsidiary's whole declaration, inserts a header open and changes only its decision and freeze — the routes' grants. See "Inventory coverage and report datasets" |
| `report_datasets` | LP3-04 PR C: one retained report dataset per capture — its exact JSON text (text, not jsonb), fingerprint, context, selection, capturer and referenced subsidiaries. Append-only (`TA016`, every writer): an insert names a frozen version of its organisation and year and agrees with its content; deleted only with its organisation. RLS on with no client policy and nothing granted to any client role, the service role included; the runtime role SELECT, INSERT. See "The capture" |
| `report_issuances` | LP3-04 PR D: one issuance per retained dataset, language, template and options (the unique key; `report_already_issued`) — its derived status and gaps, the dataset's fingerprint and referenced subsidiaries, the renderer, the issuer (opaque) and its retained PDF's opaque artifact id, object key (`<organisation>/<artifact>.pdf` in `report-artifacts`, CHECKed), size and SHA-256 of the stored bytes. Append-only (`TA017`, every writer): an insert issues a retained dataset of its organisation — year, fingerprint and referenced set the dataset's — a final only of a confirmed inventory with an included obligation and without coverage gaps; `issued_at` is the database's clock; deleted only with its organisation. RLS on with no client policy and nothing granted to any client role; the runtime role SELECT, INSERT. See "The issuance" |
| `consents` | One row per consent a person gave — today the KVKK notice accepted at self-service registration (`kind` `kvkk_registration`): the profile, the notice version shown (`text_version`), its language and `accepted_at`, stamped by the database (the runtime role cannot write it, so a consent cannot be backdated). Append-only at runtime (the runtime role SELECT and a column-level INSERT; no UPDATE or DELETE); removed only with its profile. RLS on with no policy and nothing granted to any client role, the service role included |
| `invitations` | One per invited profile (LP4-01): `status` `pending` → `sent` → `accepted`, or `revoked`; the email's language, the inviter (null for the operator), attempts and the last failed step with a short code. Operational state: RLS on with no policy and nothing granted to any client role, the service role included |
| `subsidiaries` | The company nodes of an organisation's group tree (`inc26-group-tree`, see "The group tree"): `parent_id` (null only at the root), `node_type` (`holding` · `sub_holding` · `sector_group` · `company` · `child_company`, fixed at creation), `control` (`controlled` · `associate`), `share_percent` (0–100, optional, inert), `nace_code` (optional) and `created_by_role` (null for a node carried over or written by an earlier image). A new organisation starts with one, named after itself, in its geography, tracked at subsidiary level — its root, a `holding` (UAT round 2, K1) (geography — updated only by the API, audited, or the owner: `TA015` — sector, status, included scopes, reporting contact, and `tracking_granularity` — whether completeness is measured for the whole entity or per location) |
| `locations` | Facilities within a company node — never a sector group (`TA021`) — with an optional `location_type` (`warehouse` … `rms_station`; null for a facility from before the tree) (their geography, too, updated only by the API, audited, or the owner: `TA015`) |
| `user_subsidiary_access` | The company grants of a `super_admin` or a `standard_user` (tenant‑isolation source): `(user_id, subsidiary_id, organisation_id)` with composite foreign keys that keep a grant inside one organisation, and `categories` (`text[] NOT NULL DEFAULT '{}'`), the emission categories ticked for a standard user's grant — stored sorted and unique, each one of `CATEGORIES`, validated by the API (no CHECK, as for `activity_records.category`). A super_admin's grant keeps `'{}'` and covers every category. The runtime role holds SELECT, INSERT and DELETE on the table and UPDATE on `categories` alone (column-level, pinned in `packages/db/scripts/runtime-role.mjs`), so a categories change is one UPDATE and one audit row; the keys stay insert-and-delete only |
| `audit_log` | Append‑only record of every mutation (`action`, `entity`, `entityId`, `diff`, and the acting `role` as TEXT, stored as it was at the time — never rewritten, see "Roles (RBAC)") |
| `factor_releases` | One publication loaded whole (LP3-03): publisher (a closed registry — the internal `TonyAI prototype` and `TonyAI test fixture`, and `IPCC` and `ETKB` for the TR factor package (LP4-02); `FACTOR_PUBLISHERS` in shared-types is the same list), title, edition (a label, never compared), ordinal (orders a publisher's releases; each load must exceed the last), status `authoritative` › `placeholder` › `fixture`, `withdrawn` never resolving, and provenance (source URL, licence, publication date, reviewer and review date — required for an authoritative release). Append-only: the changes it accepts are its **seal** (`sealed_at`, once, by the database's clock, in the transaction that loads it — a release left unsealed at commit is refused, a sealed one takes no row, and pricing reads sealed releases only) and then its withdrawal (status, who, when, why), each by the loader's or the owner's session (LP4-02) |
| `emission_factors` | Reference data (not tenant‑scoped): one factor of one release, keyed on `FACTOR_IDENTITY_FIELDS` (release, category, activity type, gas, geography, reporting year, Scope 2 method, calorific basis, normalised unit), quoted in kgCO2e per ONE base unit of its family, with `source` + `methodology` for traceability. Append-only; only a test fixture release's rows may be deleted (the fixture publisher's, fixture or withdrawn) |
| `factor_release_events` | The factor library's own record (LP3-03): every release load and its rows (counted per statement), seal (LP4-02), withdrawal (who, when, why) and fixture deletion — with the database role and, when the writer sets `tonyai.actor`, a firm or role — stated by the writer, never verified. Written only by SECURITY DEFINER triggers, for every writer (no release is written through the API, so `audit_log` could not see one); append-only; no client role reads it, nor the runtime role — the owner reconciles it (`runtime-role.mjs check`, `rls:probe`). A direct INSERT is refused even to the owner; an authoritative load must name its actor; a statement that would leave a rows event unrecorded is refused. Its two writers run as the owner, so each answers for its own tables only, and only the owner may execute (so attach) them — Supabase's default EXECUTE grants to the API roles are taken back, and `runtime-role.mjs check` and `rls:probe` fail if any reappears |
| `unit_conversions` | A sourced step between unit families (metered m³ → kWh) for one fuel, country and year, of one release (`CONVERSION_IDENTITY_FIELDS`). Append-only. The seed's only rows are the labelled placeholder ×11.36 for natural gas (K4) |
| `factor_parameters` | A sourced calculation constant of one release (LP4-02, D2): a leak rate per equipment type, the reference GCV and NCV, and the billed GCV range `billed_gcv_min` / `billed_gcv_max` (a pair, LP4-02 PR5) (`PARAMETER_UNITS` holds each key to one unit; `PARAMETER_IDENTITY_FIELDS`: release, key, subject, default or alternative). Loaded and sealed with its release, withdrawn with it, append-only, loader `INSERT`, runtime `SELECT` |
| `activity_records` | Core data‑entry unit (child of `subsidiaries`): one activity input per (subsidiary, location, period, category, activity type) with `parameters` (LP4-02, D3, D7: Natural Gas's calorific overrides and volume correction, or for a bill in kWh or MWh its `cvBasis`, `net` or `gross` (ng-kwh-engine; a JSON null is an absent key), a refrigerant's or a fire suppression record's equipment lines, its `kg` value being their total capacity (a Fire Suppression line names one of its three devices at the default rate, uat4-fire-suppression-entry), or an Electricity record's optional self-generation block (self-gen-model: `generationTopology`, `selfGenerationSource` (`solar`, `wind`, `natural_gas_chp`, `diesel_generator`), `selfGeneratedKwh`, and optionally `exportedToGridKwh` and `facilityConsumptionKwh`, all in kWh; all or nothing: either every field is absent or JSON null, or the topology, the source and the generated kWh are all present; the CHECK admits topology `A` only, a generation of 0 or more, exports from 0 up to the generation and a facility consumption above 0; never priced); a shape CHECK, audited, frozen with the other inputs once committed, read by the TR rules and, for the self-generation block, by the engine in every geography), a derived `scope` (its category's, a CHECK), a canonical `period_value` (a CHECK), an `activity_value` within 0…10¹² (a CHECK), an immutable `calculation` snapshot, and a `status` workflow (`draft` → `submitted` → `under_review` → `approved`/`rejected`/`locked`, plus `voided` for a figure withdrawn from the inventory; the screens call `rejected` "Returned" / "İade edildi" and the reviewer's action a return, while the stored status, the API route and the audit action keep `rejected` and `reject`, WP5). A record becomes `under_review` when a user who may approve it opens it in the review queue (WP5). The `activity_records_snapshot_immutable` trigger allows only the lifecycle's steps and freezes the inputs and snapshot outside `draft` and `rejected` (TA001). The one way back to `draft` is the author's **recall** of a `submitted` record before review starts (BUG-R2-03); the inputs stay frozen on that step itself. An approved figure is corrected by voiding it and entering a new record (D04). `updated_at` is also the edit version (`seenUpdatedAt`, self-gen-model): Prisma's `@updatedAt` sets it, to the millisecond, on every write the API makes to the row (edits, status transitions, period locks; evidence links do not touch it), and the lifecycle lock's `changedSince` relies on it too, so any future write to the row (raw SQL or a trigger included) must bump it or both checks go blind. The one exception is the one-off backfill of `submission_count` (migration `20261125120000_uat4_record_submission_count`): the count is not an input, and bumping the version across a deploy would refuse every open edit form and review sheet with `record_changed`. Also carries `submission_count` (WP5, `uat4-review-resubmit`: 0 until the first submit, set only by a successful submit, in the same compare-and-set update that sets `submitted_at`, to one more than the higher of itself and the record's `submit` audit rows (so a submit an older image made in the deploy window is counted at the next one), so it survives a recall and a return; the review queue's "Revised" badge reads it at 2 or more; backfilled from the `submit` audit rows, with a floor of 1 for a record that left `draft` without one, the seeded records included; the audit rows stay the authority on what happened), `submitted_at`, the withdrawal trio (`voided_by`/`voided_at`/`void_reason`) and the anomaly provenance pair (`anomaly_baseline_prior_count`/`anomaly_baseline_tco2e`) |
| `evidence` | A file owned by a subsidiary (private Storage object key — unique, one object per row — the original filename, and `sha256`, the hash of the bytes as uploaded; null on files from before LP1-02); uploaded through the API, never browser→Storage |
| `storage_intents` | Storage effects the database has committed to and Storage has not confirmed: `upload` (bytes sent, owning row not committed yet) or `delete` (row gone, object to remove), with attempts, last error and next attempt. Operational state, not tenant data: RLS on with no policy and nothing granted to client roles |
| `activity_record_evidence` | Which records a file backs — `(activity_record_id, evidence_id)`, both foreign keys composite over `subsidiary_id` so a link never crosses subsidiaries |
| `period_locks` | One closed reporting period for one subsidiary `(subsidiary, year, period, periodValue)` — period‑level state, because record status alone cannot block a *new* record |
| `targets` | Subsidiary‑level reduction targets with a **declared** baseline (never a computed one) |
| `subsidiary_denominators` | Per‑year intensity denominators `(subsidiary, year, metric)` so intensity over time stays comparable |

### The group tree (`inc26-group-tree`)

An organisation's companies form one tree of unbounded depth (INC-2.6 Rev.3 §2): the root is the organisation's one `holding`; a `sub_holding` or `sector_group` sits under the holding or a sub-holding, a `company` under the holding, a sub-holding or a sector group, a `child_company` under a company or a child company (`allowedChildTypes` in `@tonyai/shared-types`). A facility stays a `locations` row, the leaf under one company. The parent key is composite with the organisation (`(parent_id, organisation_id)` → `subsidiaries(id, organisation_id)`, `ON DELETE RESTRICT`), so no parent of another organisation can be stored and a node with a child is not deleted. A node holds records unless it is a sector group (a label) or an associate (outside Scope 1 and 2): `holdsRecords`.

Four `ENABLE ALWAYS` triggers hold the rules for every writer — the previous API image, the seed, the owner — with a data-only restore in replica mode as the only exemption; each message starts with the API error code it answers as:

| Trigger | Code | What it holds |
| --- | --- | --- |
| `subsidiaries_tree_shape` | `TA018` | Under an advisory lock per organisation, at READ COMMITTED: a company written with no parent goes under the root, or becomes the root when there is none (RD14); one `holding`, the only node with no parent; placement by type, never under an associate; a type never changes; no move under the node's own subtree, nor while the subtree holds a record (the subtree's rows locked first); `associate` only on a company or child company with no child, record or grant, and not declared in a year's newest boundary version |
| `activity_records_entity_open` | `TA019` | No record for a sector group or an associate; the company's row is read `FOR SHARE`, so a record and a concurrent associate tick cannot both commit |
| `user_subsidiary_access_assignable` | `TA020` | No grant for a sector group or an associate, with the same row lock |
| `locations_company_holds_records` | `TA021` | No facility under a sector group, and a facility stays with its company (its company never changes) |
| `inventory_boundary_subsidiaries_reportable` | `TA022` | No boundary declaration for a sector group or an associate — a copy or any other writer; the company's row is read `FOR SHARE`, so a declaration and an associate tick (the API locks the node `FOR NO KEY UPDATE` before it counts) cannot both commit |
| `inventory_boundaries_keep_current_reportable` | `TA022` | Deleting a year's newest version never makes the one before it — when that one declares a company since ticked associate — current again; the companies are read `FOR SHARE`, so a tick and the delete are serialised; an offboarding cascade passes |
| `subsidiaries_keep_facilities` | `TA023` | No company with a facility is deleted (RD9) by any writer, nor a company one of whose facilities was deleted earlier in the same transaction (the previous API image's sweep). A delete reached through a key's cascade (an organisation's offboarding) passes |
| `locations_note_removal` | — | Notes, for the rest of the transaction, the company of each facility deleted on its own (`tonyai.facility_removed_from`, transaction-local), for `TA023` |

Two CHECKs back them: `subsidiaries_root_check` (a node is the `holding` exactly when it has no parent) and `subsidiaries_share_percent_check` (0–100). All eight triggers and both CHECKs are pinned in `packages/db/scripts/runtime-role.mjs`. The runtime role may update `parent_id`, `control`, `share_percent` and `nace_code`, never `node_type` or `created_by_role`. An operator moving a company to another organisation now names its parent there too.

**The carry-over (2026-11-26, history).** The migration `20261126120000_inc26_group_tree` gave each organisation with companies one root: the oldest company carrying the organisation's legal name became the `holding`, or a `holding` was created as a default subsidiary is; every other company became a controlled `company` under it, with one audit row per created or changed node (no acting user, `diff.source` `migration:inc26-group-tree`, no company name). No record, grant, lock, boundary or emission figure changed; a created root is one more company, holding no record, in the KPI company count and the completeness matrix. An organisation with no company got nothing; its first company becomes its root.

## Roles (RBAC)

The four roles of INC-2.6 §1 and §6 (OpenSpec `inc26-roles-approval-chain`). Every account holds exactly one; the canonical list is `USER_ROLES` in `@tonyai/shared-types`, the same four as Prisma's `UserRole` and the `"UserRole"` enum.

| Role | Scope | What it does |
| --- | --- | --- |
| `masterkey` | The whole organisation; holds no grant | Everything: companies, facilities, period locks, targets, intensity denominators, the inventory boundary, report capture and issue (the only role that issues a **final**), void, a colleague's draft; enters records; decides a `super_admin`'s records, its own (a self-approval) and the fallback; appoints `super_admin`s and auditors, changes roles, disables and enables accounts (never its own). Nobody is made a masterkey in the product: one comes only from self-service registration, the operator's `provision` or the carry-over below |
| `super_admin` | The companies it is granted (any number) — a grant covers the node it names, never one beneath it | Enters records and decides a `standard_user`'s records in its companies; manages the facilities of its companies; creates a `child_company` under one of its companies and is granted it in the same step; writes its companies' inventory-boundary declarations inside the version the masterkey opened; invites standard users and sets their company and categories inside its own companies; reads every record trail and generates live reports within its companies. No other company write, period lock, void, boundary version lifecycle, report capture or issue, role change or account disable |
| `standard_user` | One granted company (an account carried over with several keeps them), narrowed to the categories ticked on the grant | Enters, edits, submits and bulk-uploads records only in its ticked categories; reads only those records, their evidence and the figures built from them, plus every record it created; reads the trail of its own records only |
| `auditor` | The whole organisation; holds no grant | Reads everything — records with their calculation trace, record trails, evidence, the inventory boundary, reports, captured datasets, issued reports and the organisation audit log — and changes nothing but its own language, theme and password |

**One capability table.** Every role-keyed power is a row of `ROLE_CAPABILITIES` in `@tonyai/shared-types` (`can(role, 'period_lock.write')`), pinned cell by cell against INC-2.6 §6 by `packages/shared-types/src/roles.spec.ts`; the API's services and the web's pages ask `can(…)` and list no roles themselves. A power no document gives a `super_admin` stays with the masterkey (owner ruling R4). Scope is not in the table: the guard's `accessibleSubsidiaryIds` bounds a granted role's reads and writes, and a standard user's categories bound its activity records through one record-scope rule (see [Security](security.md)). Who decides a pending record is one pure function, `recordApprover` (see [Security](security.md), "Record lifecycle").

**Report datasets and issuances** (LP3-04, W3/W4): only a `masterkey` captures and issues; a `masterkey` and an `auditor` read them (they cover the organisation); a `super_admin` and a `standard_user` neither capture, issue nor read one.

**The carry-over (2026-11-25, history).** The migration `20261125180000_inc26_roles_approval_chain` renamed the enum's values in place, in one transaction: the earlier organisation-wide `super_admin` became `masterkey`, `consultant` became `auditor`, `data_entry` became `standard_user`, `executive_viewer` accounts were folded into `auditor`, and the emptied `executive_viewer` slot was renamed to the new, company-scoped `super_admin`, which no account held afterwards. Every existing grant was kept, with all thirteen categories ticked. Each carried account got one `role_model_change` audit row (no actor; the role before and after in `diff.role`). Audit rows are never rewritten: the audit list and the record trail show a `super_admin` stored before the organisation's `role_model_changed_at` as `legacy_super_admin` (the earlier organisation-wide role, never today's scoped one), and the three retired names as stored (`displayRole` in shared-types).
